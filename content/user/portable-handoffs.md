當你切換 Provider、經由可攜式重新啟動繼續工作，或是使用 Provider 自己無法續接的 fork 時，T3 Code 會把對話的上下文轉交過去。

:::plain handoff（交接）是什麼
每個 Provider 只記得它自己參與過的對話。當 Thread 換成另一個 Provider、或是要開一個全新的 Provider session 來接手時，新的那一邊並沒有看過前面的內容。handoff 就是 T3 Code 從已存下來的對話裡挑出一部分，交給接手的 Provider，讓它知道先前發生了什麼事。
:::

短的對話會完整轉交。對於較長的對話，T3 Code 會優先保留最近的請求與回答、最初的請求，以及相關的活動，例如指令的執行結果。被選中的訊息會保留完整的文字、順序，以及是使用者還是助理說的；失敗或被中斷的 turn 裡做到一半的工作也包含在內。你的新請求是分開處理的，絕對不會為了塞進歷史紀錄而被縮短。

如果已安裝的 Codex 版本支援這項操作，Codex 會直接收到歷史訊息。其他 Provider 則會收到同一批挑選出來的內容，形式是標註了來源的對話上下文。handoff 不會複製原本那個 Provider 的推理過程、工具呼叫狀態或附件。

handoff 裡包含了指向被省略歷史的參照。agent 可以用 T3 Code 的 Thread 讀取工具，取回已儲存的訊息和活動，包含一則很長的項目裡剩下的部分。對於重要的限制條件，你還是可以在下一則訊息裡再說一次。handoff 是在額度內挑選出來的內容，不是由 agent 寫出來的摘要。

:::plain 是「挑選」，不是「摘要」
T3 Code 不會請 AI 把前面的對話濃縮改寫，而是從原本的訊息裡挑出幾則，原文照搬。沒被挑到的訊息也沒有消失，只是沒有直接放進去，agent 需要時可以自己回頭查。不過 agent 不一定會去查，所以真正重要的限制，在下一則訊息裡再寫一次最保險。
:::

## 上下文的限制 {#context-limits}

handoff 必須留出空間給 Provider 既有的上下文、你的請求與附件、指示、工具，以及後續的工作。如果連它的取回參照都放不下，T3 Code 會回報錯誤，而不是縮短你的請求。請先壓縮（compact）目標對話，或是選擇上下文較大的模型，然後再試一次。

Server 的管理者可以設定 `T3CODE_CONTEXT_HANDOFF_TOKEN_CAP`，來變更一開始分配給歷史紀錄的額度（預設 16,000；會被限制在 1,024–64,000 之間）。這是一個上限，不是對 Provider 上下文視窗大小的保證。文字的計算方式採保守估計，每個 UTF-8 byte 算一個 token，包含來源標註和 JSON 跳脫字元在內。匯入的歷史紀錄另外有一個 64,000 byte 的上限；你目前的輸入和附件內容不會佔用這個上限。

:::note 中文對話能帶過去的字數比較少
這裡的額度是用 UTF-8 的 byte 數來算的，不是用字數。英文字母一個是 1 byte，常用的中文字一個是 3 byte。所以預設的 16,000 額度，如果全部是中文，大約只放得下五千多個字，而且還要再扣掉來源標註等額外的部分。對話主要用中文時，更要記得把重要的要求在新訊息裡重寫一次。
:::

T3 Code 會使用你所選模型與選項的可用容量資訊，再搭配 Provider 回報的上下文用量資料。開啟一個全新的 Provider 對話時，會清除先前的用量，但保留已知的模型容量。變更模型或上下文視窗的選項時，會丟棄已經過時的用量和壓縮門檻。

當沒有任何容量資訊可用時，T3 Code 會假設視窗大小是 128,000 個 token。它會保留至少 16,000 個 token，或是視窗的四分之一（取較大者），給指示、工具和後續的工作使用。每張圖片會保留估計 8,192 個 token，與檔案大小無關；其他附件則各保留 4,096 個，用於它們的參照。當沒有用量資料時，既有的上下文會從已儲存的活動來估算。已知的較小視窗仍然會限制 handoff 的大小。這些都是備用的估計值，不是精確的 token 數。圖片解析度、自訂模型，以及隱藏的原生上下文都可能造成差異，所以 Provider 仍然有可能拒絕某一次輸入。

:::example 沒有容量資訊時，歷史紀錄能分到多少
假設完全沒有模型容量資訊，你的新訊息附了一張圖片，文字約 500 byte，而 Provider 既有的上下文估計是 10,000：

| 項目                                       | 數量    |
| ------------------------------------------ | ------- |
| 假設的視窗大小                             | 128,000 |
| 保留給指示、工具和後續工作（視窗的四分之一） | −32,000 |
| Provider 既有的上下文                      | −10,000 |
| 你的新訊息（文字約 500，加上一張圖片 8,192） | −8,692  |
| 剩下的空間                                 | 77,308  |

剩下的空間比預設的 16,000 大，所以歷史紀錄拿到的就是 16,000。反過來，如果既有的上下文已經很大，剩下的空間不到 16,000，歷史紀錄就只能拿到剩下的那一些；連取回參照都放不下時，就會出現上面說的錯誤。
:::
